MEASURED LIVE DEFECT IN SHIPPED KERNEL CODE. lib/attributes/class-modules.nix:128-166 applyInjectReroute. Independent of whether the confluence redesign lands - this is the current tree misbehaving.

W2 finding F1 recorded that the reroute fold is non-confluent on a CHAIN: same act set, different order, content lands in a different class. That UNDERSTATES it. On a non-tree acyclic shape the fold does not merely relocate content - IT DESTROYS IT.

MEASURED, diamond A-to-B, A-to-C, B-to-D, C-to-D, one aspect per class, through the live class-modules.compute. Four permutations of ONE act set, D's bucket:
  d_p1 = cD,cB,cA,cC
  d_p2 = cD,cB,cC,cA
  d_p3 = cD,cB,cC        <- cA NEVER REACHES D
  d_p4 = cD,cC,cB        <- cA NEVER REACHES D
FOUR ANSWERS. TWO STRAND cA ENTIRELY. Rule construction iterates builtins.attrNames policies (concern-policies.nix:400) = ALPHABETICAL, so RENAMING A POLICY can silently delete a class's content.

MECHANISM: the fold step at :156-166 is acc // { to = (acc.to or []) ++ (acc.from or []); from = []; }. On a diamond the first act to fire empties A; the second act reading A finds it already empty, so one of the two branches carries nothing to the sink.

REACHABILITY: declare is a top-level public export (lib/default.nix:2730, comment: den's declaration vocabulary - Policies read declare.member, declare.edge). declare.reroute is generated by dispatch.mkActions from the groups.resolution list (declarations.nix:54, :162) and evaluates - verified. So any policy author can reach this. Zero call sites today; zero corpus witnesses; the only reroute acts in the tree are the synthetic fixture at ci/tests/class-bucket-query.nix:65,:70, whose own header calls reroute corpus-inert. THE STANDING BAR IS DEN-SURFACE EXPRESSIBILITY, NOT CORPUS PRESENCE - see feedback_den_surface_not_config.

NO TEST COVERS IT. ci/tests/class-bucket-query.nix:99-101 exercises a chain in the ONE order that works. There is no diamond fixture anywhere in the suite, which is why F1's own proposed replacement also missed it and had to be sent back by the gate.

ACCEPTANCE: a diamond fixture that pins the answer, plus permutation invariance over the same act set. Per the owner bar, a ported valid FAILING test beats no test - if the fix lands separately, the test should land first and go red.

FIX PATH: the confluence redesign (spec 2026-07-27-class-reroute-confluence-design.md) removes this by construction, since the preimage closure has no reduction sequence to permute. That design is at REDESIGN under den-hoag-4kh.6 and has NOT entered the graph. This bead records the DEFECT, which stands on its own regardless of which fix is chosen.

### 1 — 2026-07-28T01:05:21 · Jason Bowman

SECOND INDEPENDENT DEFECT IN THE SAME FUNCTION — A SELF-REROUTE IS AN UNCATCHABLE ABORT.
Measured 2026-07-27. Separate from the diamond content-loss this bead was filed for; same site, different
mechanism, and no permutation test would ever surface it.

    declare.reroute { from = c; to = c; }
    => error: dynamic attribute 'A' already defined at lib/attributes/class-modules.nix:161:11

CAUSE: the fold step is
    acc // { ${t} = (acc.${t} or [ ]) ++ (acc.${f} or [ ]); ${f} = [ ]; }
When t == f that is THE SAME DYNAMIC KEY TWICE IN ONE ATTRSET LITERAL, which Nix rejects at eval. It is not
a throw the kernel raises — it is a language-level abort naming an INTERNAL FILE AND LINE, with no den
concept in the message.

builtins.tryEval DOES NOT CONTAIN IT. So there is no arm anywhere that can degrade, catch, or report it.

REACHABILITY: trivial whenever a reroute endpoint is COMPUTED rather than literal. The corpus already shows
computed endpoints are the normal case for the sibling mechanism - four den-configs sites use
`intoClass = _: host.class` and two use a factory-param `fromClass` (see the corpus inventory in
den-hoag-4kh's scoping comments). A policy computing both endpoints from the same source, or two policies
whose computed endpoints coincide, produces from == to with nothing in between to notice.

WHY IT MATTERS BEYOND ITS OWN SEVERITY:
- It is invisible to every test strategy this arc has used. Permutation testing varies ORDER; a self-reroute
  is a single act. The defect is in the act's SHAPE, not the act sequence.
- It means the function has TWO independent failure modes on inputs the public surface can express: silent
  content loss on non-tree shapes (this bead's original finding) and an uncatchable abort on a self-loop.
  Neither is guarded, and the second cannot be guarded from outside because tryEval does not reach it.
- Under the confluence redesign the self-loop case is a REPAIR, not a coarsening: the SCC of a self-loop has
  no outgoing edge to a DIFFERENT SCC, so the class is a sink and keeps its own content. THERE IS NO OLD
  VALUE TO COMPARE AGAINST, because the old mechanism aborts. Any parity framing on this shape is ill-posed
  in the same way it is ill-posed on the diamond.

ACCEPTANCE: a fixture declaring a self-reroute. Against the current tree it aborts; that is the point. Per
the owner bar, a ported valid FAILING test beats no test.

PROVENANCE: found while measuring the replacement design's degenerate-input table, by an agent that ran the
current fold on every shape the table claimed. It was in no brief and nobody predicted it - it turned up
because the shapes were EXECUTED rather than reasoned about.


### 2 — 2026-07-28T04:26:54 · Jason Bowman

★ OWNER CLARIFICATION 2026-07-28 — THE PARITY TARGET IS BYTE EQUIVALENCE, NOT BYTE IDENTITY.
"our target is byte equivalency not identical — ie, we don't need to guarantee the same nix merge order."
This bears on the VALIDATED confluence design and the correction is finer than "the non-goal was wrong".

WHAT THE DESIGN SAYS: §8 declares "within-bucket module order still tracks edge-declaration order" a NON-GOAL,
justified as — orchestrator's words — sorting the preimage "would REDDEN PARITY and change merge results for
list-typed options". `mode = "paths"` was chosen over `mode = "all"` partly BECAUSE paths reproduces the old
fold's concatenation order.

★ THE JUSTIFICATION AS GIVEN IS WRONG. "It would redden parity" is not a reason under the equivalence bar —
a drvPath-identical gate is a SUFFICIENT signal, never a NECESSARY one, and defending the old concatenation
order because the oracle encodes it is the v1 shape preserved by the back door. That is precisely what
[[feedback_best_framework_first]] and the corpus demotion exist to stop.

★★ BUT THE NON-GOAL MAY STILL BE CORRECT, FOR A DIFFERENT AND MEASURABLE REASON. Equivalence means the
RESOLVED CONFIGURATION is the same, not that assembly matched. For most NixOS option definitions merge is
order-insensitive and canonicalising the preimage is FREE. For options where concatenation order survives
into the resolved value — `types.listOf` accumulation, `mkOrder`/`mkBefore`/`mkAfter` interaction — a
permuted bucket yields a DIFFERENT RESOLVED VALUE, which is not merely a different assembly order and is NOT
equivalent.
⇒ THE REAL QUESTION, WHICH WAS NEVER ASKED: does any option reachable through a class bucket resolve
order-sensitively? That is MEASURABLE and UNMEASURED. If none does, the non-goal should be DROPPED and the
preimage canonicalised — removing the residual order-dependence entirely instead of preserving it
deliberately. If some do, the non-goal stands on the resolved-value argument, not on the parity-oracle one.

STATUS: this does NOT invalidate the VALIDATED verdict — the design is correct, and confluence of BUCKET
ASSIGNMENT (the actual defect) is unaffected either way. It means the design is possibly MORE CONSTRAINED
THAN IT NEEDS TO BE, and that §8's stated reason must be replaced whatever the measurement shows.

ACTION WHEN THE IMPLEMENTATION IS SPECCED: measure the order-sensitivity question first, then either drop the
non-goal or re-justify it. Do NOT carry "would redden parity" forward — under the equivalence bar it is not
an argument.

GENERAL RULE NOW RECORDED IN MEMORY (feedback_byte_equivalence_not_identity): state parity claims as
EQUIVALENCE unless identity is genuinely required and say which you mean; when a cleaner construction differs
only in assembly order, TAKE IT; oracles and corpus configs are TOOLS, not constraints; input pins are freely
bumpable. A `drvPath`-identical gate failing is a QUESTION — is the difference observable in the resolved
configuration — not a verdict.
