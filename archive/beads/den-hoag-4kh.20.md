A verification predicate (grep, census, settling test) is only evidence if its
string actually appears on the path it claims to check. Three occurrences in the
den-hoag topology arc, same shape each time — a plausible predicate returning a
clean result it structurally could not have found:

   only `resolve.to` were invisible. Would have classified a legitimate delta as
   a bug in the rung.
2. **D6's settling test** greped `mkInstanceRegistry` to enumerate mkDen-direct
   fixtures — but den-hoag builds the registry internally, so such a fixture
   never writes that string. The grep returned empty whether or not dependents
   existed, and the plan read that emptiness as authorization to delete a live
   mechanism.
3. **Strip-site completeness grep** was `grep -rn '__entry\|…' lib/ | grep -i

**How to apply:** before trusting a verification predicate, ask *what does the
at-risk path actually look like in source* — then confirm the predicate matches
a known-positive instance. If it can't find one you already know exists, the
predicate is broken, not the code. Prefer the literal that survives lowering
(the key name, the constructor) over the conceptual name. An **absence** result
deserves more scrutiny than a hit: a hit is self-evidencing, an empty result is
indistinguishable from a blind predicate.

with `[^}]*` cannot span a nested interpolation, so it missed three id-construction
sites — including one (`fleet.nix:95` `cid`) sitting in plain view, which is the
known-positive that would have exposed it immediately. Working predicate for Nix

## The same disease in tests: a check that a degenerate result satisfies

**When an assertion quantifies over a computed set, pin the set's contents too —
otherwise a regression that empties the set passes.** `builtins.all f xs` is
vacuously true at `xs == [ ]`, so "every pair names a real node" was satisfiable
by emitting no pairs at all. Fix: assert the literal expected ids beside the
invariant.

Its twin, from the same arc: an M7 abort fixture went green because a *different*
guard (B2 stratum coherence) aborted first — the intended guard was never reached.
Caught only by a control asking **"does this test depend on the RIGHT thing"**
(point it at a single-attachment target and require red), not the weaker
**"does it depend on anything"** (remove a declaration and require red), which
passed either way.

**How to apply:** for any new guard or invariant, prove it can fail *for its own
reason* before trusting a pass. Unreachability claims need this too — an
unreachable-path abort is untestable, so prefer recording *"unreachable in this
shape, measured"* with the counter-shape named over adding a guard you cannot arm.
Three unreachability claims were asserted and disproved in one arc.

## The general form: instruments, not just predicates

**A NEGATIVE RESULT REQUIRES A POSITIVE CONTROL ON THE SAME INSTRUMENT, IN THE SAME
RUN.** Not "a known-positive somewhere" — the *same* instrument, the *same*
execution. Without one, *"it didn't fire"* and *"it cannot fire"* are the same
observation. A grep that cannot match its target and a probe that cannot fire are
one failure in two costumes.

Twice in one investigation (den-hoag `ljr`), each a step from being read as a
finding:

1. **Silence.** Two conditional throws both stayed quiet. Worth nothing alone. An
   **unconditional marker** at the same site, firing on *both* sides, is what
   converted two silences into "both links intact".
2. **The wrong observable.** A *collision* trace proves a merge descended but
   cannot separate "instrument never fires" from "code never does it".
   Re-instrumenting the *recursion branch* **tagged by depth** — family level as
   the known-positive that MUST fire (8×/15×), member level as the violation
   (0×→1×) — made the base zero a real negative.

**Corollary — apply it to the FIX, not just the diagnosis.** The first
`familyMerge` guard put its check inside the value lambda and never fired under
`attrNames`: the guard reintroduced the exact silent-until-used shape it existed to
remove. Review missed it; *arming* it caught it. So an assertion that a new guard
fires for its own reason is mandatory, never a precaution.

**And when a guard replaces an assumed invariant, the prose must change with it.**
A comment claiming uniqueness "by construction" beside code that now aborts because
it does not is this same defect in documentation form. A documented invariant that
nothing enforces is a comment, not a guarantee.

## A control must be forced to the SAME DEPTH as the subject

**Two false cleans in one probe, either of which would have certified a dead
option as safe:**

1. **Laziness hides the check.** A control setting a nonexistent option returned

2. **The harness reshaped the value.** The test driver did

⇒ **When a harness transforms the value under test, the harness is part of the
instrument and needs calibrating too.** Ask what depth your control actually

## The fixture form: it cannot disagree with the code it was written against

Reached **three times independently in one day**, from different directions:

1. **It asserts its own premise.** A fixture hand-stamped the `id_hash` it then

## Papering over the TEST, not the requirement

**An acceptance criterion that is already satisfied gives the requirement no
falsifier.** Nothing observable then distinguishes implemented-correctly,
implemented-wrongly, and not-implemented — rule 1's failure mode applied to
acceptance rather than to a probe. Watch for it when a criterion is *proposed as
a concession* ("accept that X is excluded by the existing gate"). Ask: does this
criterion hold **today**? If yes, it tests nothing.

Related traps, each earned:
- **A cited finding is still a claim until its mechanism is traced.** A finding
  that arrives with a `file:line` gets adopted verbatim; a reviewer's own error
  propagated one full revision this way.
- **A comment stating a constraint is evidence** — contradicting one needs a
  measurement, not a recollection. **But a comment describing an ABSENCE is not a
  law.** *"X never happens by Y"* may be true only because Y does not exist yet,
  and will read as a prohibition on exactly the feature that adds it. Test:
  *does this describe what the code guarantees, or what it merely does not do yet?*
- **An armed conjunction needs one perturbation per conjunct**, each moving only
  its own — one dead conjunct hides inside a `true`.

Related: agents' **absence claims** need the same scrutiny — two in this arc were
false (den v1 reported "not on this machine" when it sits at
`~/Documents/repos/denful/den`; `deriveGroup` reported missing when the dir is
`gen-derive`, not `gen-dispatch`). Positive findings held up; absence claims did
not. See [[feedback_scout_vs_ultracode_audit]].

The sharpest instance yet, because nothing about the run looks wrong. `grep '2\.3'

## The TOOL itself can return a false zero — cross-check with a second one

One agent reported `grep -rnE` through a harness wrapper returning **0 hits** in a file where a direct grep
returned 28; it cross-checked with `ripgrep` rather than trusting the zero. **That specific fault did NOT
reproduce** — a second agent got identical counts from `grep -rnE`, per-file `grep -nE`, and `rg -n`, and
found the likelier cause of its own earlier zero was a *relative* path with the working directory resetting

session-wide instrument fault and propagated it to three agents before it was checked.

**The discipline survives the retraction, on its own merits.** A relative path that silently resolves
elsewhere produces exactly the same false zero as a broken tool, and *that* is common. Cross-checking is also
what closed a real completeness question in the same arc: a sweep for ordering guards under **non-local
spellings**, with a positive control that fired on the one row the primary predicate structurally could not
see, converted "the table is asserted complete" into "the table is measured complete".

⇒ **A negative from a recursive/wrapped search deserves a second instrument before it is reported.** The
positive-control rule catches a predicate that cannot match; it does **not** catch a tool that does not
traverse. Confirm an absence with a different tool (`rg` vs `grep`) or a direct per-file read, and prefer
per-file over recursive whenever the answer is load-bearing.

**Same class: a tool that silently omits the field you queried.** `bd show --json` returns no `comments`
key at all — only `comment_count`. Querying it for comment content yields nothing, indistinguishable from

JSON alone*. The agent that settled it went to the raw store (`.beads/beads.jsonl`) instead of trusting
either the renderer or the JSON. **When an absence claim rests on a tool's output, check that the tool
actually carries the field** — and go to the storage layer when the answer matters.

## Timing: work-dominated reproduces, floor-dominated does not

A wall-clock figure was called an "internal impossibility" because a traversal

floor against *their* traversal number. Three machines measured three different

Evidence: the same exponential arm came in at 12.417 s and 12.473 s on two machines
while the floors disagreed by 16×. Quote a floor-dominated number only labelled
environment-specific and never load-bearing; rest the claim on the **shape**.

════ ★★★ TRAP (2026-08-10, measured on a live reversal): AN INSTRUMENT CONTROL IS NOT A DOMAIN CONTROL ════
A positive control proves THE INSTRUMENT FIRES. It says NOTHING about whether the instrument is POINTED AT

THE CASE. A gate ran controls all session and discarded two runs whose controls failed to fire -- an

was a SCALING claim ("the real graph sits at the linear end"). Linear-versus-quadratic is a statement about
how structure behaves AS THE POPULATION GROWS, and it was evaluated at a single point of a population that
is not the one that grows.
· A WRONG-KIND proxy (entity graph rather than policy atoms) can still bound shape parameters if the induced
  structure carries over -- that bound was stated and was honest.
· A WRONG-POPULATION proxy CANNOT ANSWER A SCALING QUESTION AT ALL. ⇒ VOID, not bounded, not attributable.

the artefact under review and NOT ONCE to the reviewer's own excursion. Auditing an artefact's domain and
never auditing your own is the shape. Before publishing a figure, ask the question separately from the
control: IS THIS THE POPULATION THE PROPERTY QUANTIFIES OVER? An instrument that fires is not an answer to it.

════ ★★ TRAP: A PRESENCE COUNT OVER AN IGNORABLE FILE DIFFERS BY INSTRUMENT — filesystem vs git ════
Measured 2026-08-10 across 23 sibling gen repos, both controls in the same run (`zzz-nope.md` => 0/24,
`flake.nix` => 24/24):
    test -e '.envrc'        => 14
    git ls-files '.envrc'   => 13
The divergence is ONE repo — gen-rebuild — which has an `.envrc` ON DISK that git does not report.
★ THE CAUSE IS THE IGNORE RULE ITSELF: `.envrc` matches a GLOBAL gitignore (`~/.config/git/ignore:18`,
beside `/AGENTS.md` at :22 — and note :20 is a DUPLICATE `/AGENTS.md`, so `git check-ignore` reports the
LAST match). An ignorable file can therefore sit untracked in a working tree: PRESENT TO THE FILESYSTEM,
ABSENT FROM EVERY CLONE. Which number is "right" depends entirely on the question — "does the author have
one" versus "does a fresh checkout get one" — and a presence count that does not name its instrument answers
neither.
⇒ FOR ECOSYSTEM CONFORMANCE, `git ls-files` IS THE INSTRUMENT: the standard a new repo must match is what a
clone receives, not what happens to be lying in someone's tree.
★ AND `git check-ignore` HAS THE MIRRORED DEFECT, measured the same day: WITHOUT `--no-index` it SKIPS
TRACKED PATHS — empty output and exit 1 for files that ARE ignored but tracked, i.e. a false negative in the
direction that matters. `core.excludesfile` is unset here, so consulting it gives a false negative too.
Use `git check-ignore --no-index -v`, with a known-not-ignored file (`README.md`) as the live control.

★ THIS IS THE SAME FAMILY AS THE `.worktrees/` HAZARD ALREADY BANKED — git-visible-not-readable trees where
git and filesystem sweeps ENUMERATE DIFFERENT SETS. The general rule: WHENEVER A COUNT RANGES OVER FILES,
STATE WHETHER IT WAS TAKEN FROM GIT OR FROM THE FILESYSTEM, because for any path matched by an ignore rule
the two are different measurements of different populations, and both can be correct.



════ ★★★ THE NULL-RESULT CONTROL: WRITE DOWN WHAT "NOTHING" HASHES TO, BEFORE YOU RUN THE SWEEP ════
Measured 2026-08-10 on a rev sweep, and it is the cleanest defence anyone has produced this session
against the whole `2>/dev/null` family.

THE SETUP: a gate verified one file was unchanged across five revisions via
`git show $r:specs/... | md5sum`, with `2>/dev/null` on the git call. All five revisions returned
**`d41d8cd98f00b204e9800998ecf8427e`** — identical, which is exactly the shape of "confirmed unchanged".
IT IS THE MD5 OF THE EMPTY STRING. zsh parsed `$r:s...` as a PARAMETER-EXPANSION MODIFIER (`:s` =
substitute), so the revspec was never valid; `2>/dev/null` swallowed the error; and `md5sum` hashed
nothing, five times, agreeing with itself perfectly.
⇒ FIX: quote it — `git show "${r}:path"`. ★ THIS EXACT TRAP IS ALREADY IN THE PROJECT'S BOOT PROMPT
(recorded for `$r:l`, the lowercase modifier) AND A FRESH-CONTEXT AGENT WITH NO ACCESS TO THAT LIST HIT
IT ANYWAY. The recurrence is the evidence: it is not an exotic slip, it is what this shell does to an
ordinary-looking command, and it will keep happening to whoever does not carry the list.

★★ WHAT ACTUALLY CAUGHT IT — the technique worth copying, and it cost one line:
**THE AUTHOR HAD WRITTEN DOWN `d41d8cd98f00b204e9800998ecf8427e` IN ADVANCE, SPECIFICALLY SO A NULL
RESULT COULD NOT MASQUERADE AS AGREEMENT.** Without that line the report would have read "verified
unchanged across all five revisions" — and it would have been TRUE BY LUCK, which is strictly worse than
being wrong, because the method survives to be used again on a case where the answer differs.
⇒ GENERALISE IT: whenever a sweep's PASS CONDITION IS AGREEMENT (all hashes equal, all counts equal, all
diffs empty), the degenerate value is a passing answer. Compute what the instrument returns on NOTHING
and assert against it. For md5 that is `d41d8cd98f00b204e9800998ecf8427e`; for `wc -l` it is 0; for a
`comm` diff it is empty on both sides — which is why an empty-set-difference check needs its own positive
control (drop a member, confirm the predicate names it).

★ AND THE STANDING RULE THIS SHARPENS: `2>/dev/null` CONVERTS A BROKEN INSTRUMENT INTO A CLEAN-LOOKING
ABSENCE. Already banked for missing binaries; this instance extends it to a MALFORMED ARGUMENT, where the
command exists, runs, and produces empty output that flows downstream into something that will happily
consume it. The stderr you suppressed is the only place the failure was visible.



════ ★★★ TRAP: A NEGATIVE CONTROL CONTAMINATED BY THE THING IT CONTROLS ════
Measured 2026-08-10. The sharpest instrument failure of the session, and one nobody here had stated before.

A gate swept an artefact with a negative control token `zzz-nope` — the standard "this must return 0"
guard proving the predicate is not matching everything. **IT RETURNED 1.** Not because the sweep was
broken: because THE ARTEFACT UNDER REVIEW USED THE SAME TOKEN AS ITS OWN CONTROL. The document being
measured had `zzz-nope` written into it, as ITS author's negative control, for exactly the same reason.
⇒ THE CONTROL AND THE SUBJECT SHARED A NAMESPACE. Re-run with `qqxzv-control` => 0, live positive
`gen-rebuild` => 9.

★ WHY IT MATTERS BEYOND THE ONE CASE: a negative control's whole job is to be ABSENT FROM THE DOMAIN. The
more standard and memorable the sentinel, the more likely a careful author has already used it — and
CAREFUL AUTHORS ARE EXACTLY WHO YOU AUDIT. So the failure rate of a shared sentinel RISES with the quality
of the artefact. A control that fires tells you the predicate works; it does NOT tell you the hit came
from the domain rather than from the control's own twin.
⇒ RULE: A NEGATIVE CONTROL TOKEN MUST BE UNIQUE TO THE RUN, not merely improbable. Generate it per-sweep,
or namespace it to the auditor, and if it fires, CHECK WHERE IT MATCHED before concluding the predicate is

════ ★★★ TRAP — A COUNT OF A DOCUMENT, STATED INSIDE THAT DOCUMENT, FALSIFIES ITSELF ON BEING WRITTEN
(measured 2026-08-11, engine-spec amendment round; found by the author BY RE-RUNNING, not by reasoning) ════

THE INCIDENT. An author establishing that a term had disappeared from an artefact wrote into that artefact:
"`gen-settings` occurs ZERO times in this document." The measurement was TRUE when taken against the
worktree. **The sentence recording it names `gen-settings` — so writing it made it false.** Worktree count
on completion: 2. The claim was self-refuting at the instant of publication, and no re-run of the ORIGINAL
predicate would ever show it, because the predicate was correct when run.

THE LAW. **A count OF a document, asserted INSIDE that document, is invalidated by the act of assertion
unless it is REV-EXPLICIT.** State it against a frozen revision — `git show <rev>:<file>` or a blob SHA —
never against the worktree. The rev-explicit form is immune because the counted object can no longer change.

WHY IT EVADES THE STANDING INSTRUMENTS, which is what makes it worth an entry:
· It is NOT a stale figure — R§A.2's "re-run before citing" does not catch it; re-running the stated
  predicate at the stated moment gives the stated answer.
· It is NOT a wrong predicate — the domain and quantifier match (predicate-blindness law, satisfied).
· It is NOT a missing control — a live control passes cleanly beside it (here `gen-demand` ⇒ 18, same
  instrument same run).
· The defect is REFLEXIVITY: the measuring act mutates the measured domain. Only re-running AFTER the edit
  exposes it, and nothing in the standing law tells anyone to do that.

THE DETECTION RULE, generalised past this artefact: any claim of the form "X occurs N times here / X is
absent from this document / this document contains no Y" is EXPOSED. Sweep for that shape whenever an
artefact asserts a count of itself, and check each against the rev the claim names — if it names no rev, it
is defective by construction regardless of its number.
★ THE SAME SHAPE REACHES BEADS AND SPEC PROSE, not only gated documents: a bead body asserting "no bead
mentions Z" becomes false the moment it is saved, and the graph is exactly where absence claims get made.

COMPANION FALSE-POSITIVE FROM THE SAME PASS, cheap and recurrent: unbounded `thin` over prose ⇒ 2 where the
true count is 1 — the second hit was **`one thing`**. `thin` matches inside `thing`, `nothing`, `something`.
USE `\bthin\b`. The word-boundary form is what the register cell states; the raw form silently inflates.
